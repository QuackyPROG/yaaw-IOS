# YAAW-iOS investigation report — 2026-10-15

This document records the investigation that preceded the v0.1 implementation.

## YAAW-SE findings

Reference: `QuackyPROG/yaaw-SE`.

Reusable invariants:

1. **Agents are disposable; artifacts are durable.** Conversation history is not project memory.
2. Canonical semantic logic belongs in one compact framework root.
3. Durable project truth and replaceable runtime coordination are separate.
4. Roles define authority; modules add expertise.
5. Orchestrator owns observation/routing, not product, architecture, implementation, or acceptance.
6. Implementer cannot self-approve.
7. Reviewer acceptance binds to concrete repository/artifact/evidence identity.
8. Installer writes are boundary checked, hash tracked, transactional, and must preserve durable project memory.
9. Provider adapters contain execution/discovery configuration, not duplicate workflow semantics.
10. Framework integrity failures fail closed.

Intentionally not copied:

- `.yaaw-core/` namespace, because coexistence with YAAW-SE must not collide.
- generic language modules that do not materially improve iOS engineering.
- multi-provider parity in v0.1; Codex is first-class.
- YAAW-SE historical project-schema migration chains.
- YAAW-SE global `yaaw` CLI alias.

## Current Expo / React Native baseline

Checked against Expo and React Native primary documentation on 2026-10-15.

- Expo SDK 57 was released 2026-06-30 and includes React Native 0.86.
- Expo SDK 58 entered beta on 2026-09-15, so v0.1 must not treat SDK 58-only APIs as stable defaults.
- React Native 0.87 is independently stable upstream, but Expo SDK 57 remains on RN 0.86; Expo projects should follow the Expo compatibility line instead of forcing upstream RN latest.
- Expo Router native tabs are `expo-router/unstable-native-tabs` in SDK 54–57. Documentation shows `expo-router/native-tabs` for SDK 58+.
- iOS 26 system navigation adopts Liquid Glass behavior when compiled with the current Apple toolchain. Expo Router documents iOS 26 header behavior and SDK-specific caveats.
- Development builds are the production-grade Expo development path when native libraries/configuration matter. Adding native code or changing native app configuration requires rebuilding the native app.
- EAS Build can compile iOS in the cloud from any host OS; Windows does not need local Xcode for cloud builds.
- For **EAS iOS device builds**, Expo requires Apple Developer Program signing credentials (or previously uploaded credentials managed by an authorized team member). Expo documents local Xcode builds as the only path to install a development build on an iPhone without a paid Apple Developer account; that local path is not available on Windows.
- EAS Workflows provides cloud build/test orchestration. Expo documents iOS simulator E2E with Maestro; the pre-packaged Maestro job is currently alpha.

## Apple platform strategy

Apple HIG guidance was checked on 2026-10-15.

- Liquid Glass is a functional material layer for controls/navigation, not a content-layer aesthetic.
- System components should be preferred because they automatically adopt platform behavior.
- Custom glass should be sparse and must preserve legibility under reduced transparency/increased contrast.
- Accessibility is a verification requirement: semantics, Dynamic Type, VoiceOver, motion/transparency settings, contrast, focus behavior, useful error communication, and sufficiently large interaction regions.
- SF Symbols are preferred where the system symbol expresses the intended meaning.
- Layout must adapt to safe areas and device classes; no iPhone 15 Pro Max dimensions are hard-coded.

Primary sources:

- https://developer.apple.com/design/human-interface-guidelines/
- https://developer.apple.com/design/human-interface-guidelines/materials
- https://developer.apple.com/design/human-interface-guidelines/accessibility
- https://developer.apple.com/documentation/technologyoverviews/liquid-glass

## Windows iPhone diagnostics

Optional tooling was researched, but is not a core dependency.

`pymobiledevice3`:

- runs on Windows, Linux, and macOS;
- supports USB device discovery, apps, syslog/oslog, crash reports, screenshots and additional DVT developer services;
- documents Windows Apple Mobile Device Service requirements;
- iOS 17+ developer services use RemoteXPC/RSD tunnels;
- no-root in-process userspace tunneling exists for supported operations, but external processes such as LLDB cannot use the in-process tunnel address.

`go-ios` / Mobile MCP:

- useful for optional device detection/tunneling;
- Mobile MCP's documented real-iOS-device workflow requires WebDriverAgent already running;
- its documented WebDriverAgent provisioning step uses Xcode/xcodebuild on macOS;
- therefore physical-iPhone autonomous UI automation is capability-detected, never assumed.

## Architecture decisions

### AD-001 — standalone workflow

Decision: standalone YAAW family member, not a YAAW-SE extension.

Reason: YAAW-SE exposes strong invariants but no demonstrated extension/profile ABI that can safely own iOS-specific lifecycle/environment semantics.

### AD-002 — framework root

Decision: `.yaaw-ios/`.

Reason: avoids collision with `.yaaw-core/` and allows both workflows to coexist in one repository.

### AD-003 — npm / CLI namespace

Decision: package and binary `yaaw-ios`.

Reason: no claim on YAAW-SE's `yaaw` alias.

### AD-004 — authorities

Decision: Orchestrator, iOS Environment, PRD, iOS Planner, Implementer, Reviewer.

The Environment authority is separate because host/device/build capability facts are neither product meaning nor architecture.

### AD-005 — artifacts

Durable truth is split across product, engineering, environment, device, research, specs, tickets, evidence, reviews, and rules. No mega-state file.

### AD-006 — execution layers

Every verification record names one environment: `windows-local`, `eas-ios-simulator`, `eas-build`, `physical-iphone`, `manual-device`, or `automated-device`.

### AD-007 — Expo project strategy

Inspect first. Bootstrap only an actually empty repository. Default new-app baseline is Expo + TypeScript + Expo Router + development build + EAS. Dependencies are added only when justified.

### AD-008 — native boundary

Every implementation/review classifies changes as one of:

- `JS_ONLY`
- `EXPO_MANAGED`
- `CONFIG_PLUGIN`
- `NATIVE_REBUILD_REQUIRED`
- `CUSTOM_NATIVE_MODULE`
- `MACOS_REQUIRED`
- `UNSUPPORTED_ON_CURRENT_HOST`

### AD-009 — testing

Static/unit/component checks run locally where possible. iOS simulator E2E is routed to EAS/macOS. Hardware-sensitive acceptance requires physical-device evidence.

### AD-010 — Codex execution

Root session remains Orchestrator. Worker roles are project-local Codex agent configurations. Reviewer handoffs require a fresh context marker.

### AD-011 — installer

Package-managed system/provider files are hash-tracked and repaired transactionally. `.yaaw-ios/project/**` is initialization-only.

### AD-012 — coexistence

YAAW-iOS does not modify `.yaaw-core/**`. Codex config uses a dedicated managed block and dedicated agent names prefixed `yaaw_ios_`.
